## RAG 和 Agent 的区别

| | RAG | Agent |
|---|---|---|
| 谁决定"做什么" | 代码 | llm |
| 流程 | 用户问 → 检索 → 塞 prompt → 回答 | 用户问 → 模型想 → 调工具 → 看结果 → 再想 → 回答 |
| 典型场景 | 知识库问答 | 订机票、改代码、处理工单 |

**一句话总结**：
RAG 是"查资料后回答"，Agent 是"自己决定做什么，然后去做"。
## 模型能真的"调函数"吗

**答案**：
不能

**那 Function Calling 到底是怎么工作的**（用"指挥 / 手"的类比说）：
llm是脑子 代码是手 脑子想手发指令请求调用

## 一次完整的调用循环（六步）

① 发请求（带工具清单）
   ↓
② 模型返回 tool_calls（"我要调 xxx"）
   ↓
③ 你的代码执行工具，拿到结果
   ↓
④ 把"模型的调用请求" + "工具的执行结果" 都追加进 messages
   ↓
⑤ 再发一次请求
   ↓
⑥ 模型这次返回普通文字 → 结束

**⭐ 为什么第 ④ 步（把调用请求也追加进 messages）不能省**：
不加模型不知道已经调用过工具了

## 工具定义的四个字段

| 字段 | 作用 |
|---|---|
| `name` | 工具名字 |
| `description` | 工具说明书 |
| `parameters` | 工具参数 |
| `type` | 工具类型 |

**⭐ 为什么 `description` 最重要**（举一个"写得烂"的例子）：
“搜索” 搜索什么?用什么搜索？怎么搜索向量还是关键字抓取？

## 四个必须理解的细节

| 细节 | 不写会怎样 |
|---|---|
| ① `messages.append(msg)` | 模型不知道自己调过工具，会反复调同一个 |
| ② `tool_call_id` 要配对 | 一次调多个工具时对不上号，报错 |
| ③ 工具出错返回 error，不抛异常 | 抛异常会中断循环，模型没机会改正 |
| ④ `MAX_STEPS` 保险丝 | 模型可能死循环，一直烧钱到超时 |

**⭐ 为什么 "工具出错要返回 error" 是 Agent 的核心思维**（对比普通接口）：
接口是给人看的 人看到报错会按照对应错误信息做出下一步反应
agent报错直接不执行了，error会被视作提示词，让llm做出下一步反应

**原因**：

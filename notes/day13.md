## `BackgroundTasks` 是什么

```python
bg.add_task(耗时函数, 参数1, 参数2)
return {"queued": True}
```

后台任务 bg.add_task(耗时函数, 参数1, 参数2) 只是加进任务列表，像是餐厅后厨把你的单子挂在了墙上还没做


**用"取外卖"类比**：

| | 同步 | 后台任务 |
|---|---|---|
| 你做什么 | 死等 | 拿到订单号等 |
| 体验 | 锁死 | 灵活等的时间可以干别的 |

**这里的"取餐号"对应代码里的什么**：

job id

## `services/jobs.py` 里的两个关键细节

### ① `db.get(Job, job_id)` 和 `db.query(...).first()` 有什么区别

2.0 写法 db.get是最新的写法

### ② ⭐ 为什么"每处理一条就 `db.commit()`"

提交每一处改动的细节 不commit每一处改动都在session里 没进入到数据库

**如果不提交，会发生什么**：

所有修改都留在会话里，没落库

**用包子店的小黑板类比**：

你做 100 个包子，每做好一个就在门口小黑板上划一道 → 排队的人随时知道进度。
要是等 100 个全做完再一起划 → 门口的人从头到尾都不知道你做到哪了，还以为你跑了。

## `routers/jobs.py` 里最重要的一行注释

## ⚠️ `BackgroundTasks` 的四个硬伤

| 局限 | 后果 |
|---|---|
| **没有任务句柄** | 不能取消、不能查、不能重试 → **所以你得自己建 jobs 表** |
| **进程重启就丢** | 你改代码触发 `--reload`，**跑到一半的任务直接消失**，`status` 永远卡在 `running` |
| **同进程内执行** | 不占 worker 池，**会拖慢主服务**（尤其是 CPU 密集任务） |
| **不能跨机器** | 多实例部署时，**任务只在收到请求的那台机器上跑** |

**⚠️ 第 2 条你现在开发时天天会遇到，具体是什么现象**：

**生产级方案有哪些**：
| 工具 | 是什么 | 适合 |
|---|---|---|
| **Celery** | **功能最全的"任务调度框架"** | 中大型项目，任务复杂 |
| **RQ** | **简化版 Celery** | 中小项目，任务简单 |
| **ARQ** | **异步版**，原生 asyncio | 纯 async 项目 |
| **云服务** | **托管的队列**，不用自己运维 | 已在云上，怕运维 |

**面试题：你的项目怎么处理耗时任务**（写出你的答案）：
"轻量任务用 BackgroundTasks，但它不能持久化也不能跨进程，所以只适合开发/演示。生产上要上 Celery 这类任务队列，任务存 Redis，worker 独立部署。"

| 问题 | 如果答案是 |
|---|---|
| 任务跑多久？ | **< 30 秒 → 不用队列** |
| 丢一次能重跑吗？ | **能，且不心疼 → 不用队列** |
| 要多机部署吗？ | **单机够用 → 不用队列** |
| 任务复杂吗（重试/定时/链式）？ | **简单 → RQ 就行** |


真正需要上 Celery 的场景：
- 线上服务，任务不能丢
- 用户量上来，要加机器
- 每天定时跑报表
- 失败了要自动重试

| 方案 | 解决的问题 |
|---|---|
| **`BackgroundTasks`** | "别让用户等"——**但只在单进程、不重启的前提下有效** |
| **Celery** | 上面四条 + 重试/定时/任务链 —— **功能全，代价是复杂** |
| **RQ** | 上面四条 —— **够用、好学** |
| **ARQ** | 上面四条 —— **专为 async 项目** |
| **云队列** | 上面四条 + **不用自己运维** |

假设两个任务同时处理同一批 100 条笔记：
问题	后果
重复调用 API	钱 × 2
重复写 message	后完成的覆盖先完成的
done 计数错乱	两个任务各加各的，互相覆盖，显示 137/100 这种鬼数字


怎么防（面试常问）
手段	思路
任务租约	jobs 表加 locked_by / locked_until，领任务前先抢锁
数据库行锁	PostgreSQL 的 SELECT ... FOR UPDATE SKIP LOCKED —— 多个 worker 抢同一批任务时不会重复领
幂等设计	同一任务跑两次，结果一样（比如用 job_id 做唯一键）
只允许一个任务在跑	创建任务前检查有没有 running 的任务，有就拒绝

FOR UPDATE SKIP LOCKED 是分布式任务队列的核心技巧 —— Celery、RQ 底层都在用类似机制。

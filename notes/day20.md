## 答案质量的三个维度

| 维度 | 问的问题 | 为什么重要 |
|---|---|---|
| 相关性 | 回答和问题之间的相关性 | 答非所问 |
| 忠实度 | 回答是否有原文依据 | llm自己编原文引用 |
| 完整性 | 关键信息 | 原文说了很多但只答了一部分 |

**为什么说"忠实度最要命"**：
相关性差 = 用户觉得没用
完整性差 = 用户觉得不够
忠实度差 = 用户在不知情的情况下被误导（难以察觉）

RAG 存在的意义就是"忠实于资料"。忠实度崩了，RAG 就白做了。

## 三条评测路

| 方式 | 优点 | 缺点 |
|---|---|---|
| 人工评分 | 最准 | 慢 成本高 cant scale |
| 规则判断 | 快 免费 | 只能判很窄的东西（比如"有没有引用"）代码差不了语义偏离 |
| LLM-as-Judge | 快 能理解文本 | 裁判的模型质量 以及在高质量模型也有缺陷 |

**现实中的做法（三步）**：
mix
① 规则：快速筛掉明显坏的（没引用、空答案）
② LLM：对剩下的逐条打分
③ 人工：抽检 10%，校准 LLM 的分数
**⚠️ 为什么"人工抽检"不能省**：
如果你不抽检，你根本不知道"LLM 裁判"靠不靠谱。
它可能给你的烂答案打高分，然后你拿着这个分数去面试 —— 一问就露馅。
## LLM-as-Judge 怎么做

**输入是什么**：
把【问题 + 参考资料 + 候选答案】一起交给另一个模型，
让它按维度打分。
**为什么必须输出 JSON**：
方便打分算平均
llm倾向于产出人能听懂的话，而不是冷冰冰的机械语言
eg：llm： 相关性方面，我认为可以给 4 分
    json：
    {
    "relevance": 4,
    "faithfulness": 5,
    "completeness": 3,
    "reason": "答案基本回答了问题，内容都能在资料里找到依据，但漏掉了第三步。"
    }

且就算再llm里限制输出json模板 亦或者让其列出公式做出平均分
llm会出错 但是模型不会出错
且在大量数据计算时这种差异就会被放大

## ⚠️ 裁判的三个偏差

| 偏差 | 表现 | 缓解 |
|---|---|---|
| 偏爱长答案 | 长答案得分高 | prompt输入长答案不作为评分加分项 |
| 偏爱自己的输出 | 同模型as judge 得分会高 | use different one |
| 位置偏差position bias | 模型会倾向于某一位置 | 打乱顺序各判一次取平均值 |

位置偏差是"偏爱前面"还是"有的偏后、有的偏中"？
答案：不一定。位置偏差的方向，取决于模型、版本、任务。
三种已知偏差
类型	表现	常见程度
Primacy bias（首因）	偏爱第一个	最普遍
Recency bias（近因）	偏爱最后一个	较少见，但存在
Middle bias（中位）	偏爱中间的选项	在"多选一"时出现

范式	做什么	输入	输出
Pointwise（点式）	给一个答案打分	1 个答案	分数（1-5）
Pairwise（成对）	比两个答案谁好	2 个答案	A / B / 平局
Listwise（列表）	给多个答案排序	N 个答案	排序列表


## 幻觉率

**定义**：
答案里有多少内容，是资料里没有依据的。
**三层做法，从粗到细**：

层	做法	能抓到什么
① 有没有引用	答案里有 [1] [2] 吗	完全没引用的 = 可疑
② 引用是否有效	[3] 存在吗（只检索了 5 块）	编造引用编号的
③ LLM 判忠实度	逐句问"这句在资料里有依据吗"	真正的内容幻觉

## 评测集里为什么要放"陷阱题"

**陷阱题看什么**：
因为你要测的不只是"会不会答对"，还有"会不会瞎编" —— 而后者只有陷阱题能测出来
陷阱题看什么？
看它的三种反应
反应	评价
① 拒答："资料里没有相关内容"	✅ 正确
② 硬编：编一个看起来合理的答案	❌ 最差
③ 半答：答了部分，但资料不够	⚠️ 次差

而且"半陷阱"才是真正的考验
什么叫"半陷阱"？

资料里有相关信息，但不足以回答问题。

例子：
问题：2026 年的销售目标是多少？

资料：（只有）2025 年销售额为 1000 万元，同比增长 20%。
⚠️ 这里既有相关性，又答不了问题。
反应	评价
✅ "资料里只有 2025 年的数据，没有 2026 年的目标"	正确
❌ "2026 年目标是 1200 万元"（自己算出/编出来的）	幻觉


⭐ 半陷阱比"完全无关"更能测出问题 —— 因为模型有"素材"可以瞎发挥。

**如果评测集全是"有答案"的题，会漏掉什么**：

三个盲区
漏掉什么	后果
① 拒答能力	系统可能"什么都不敢拒"，所有问题都硬答
② 幻觉率	所有题都有答案，模型照抄就对 —— 测不出它会不会编
③ 上线后的真实分布	真实用户有 20~40% 的问题是"域外"的

def run_canary_test() -> None:
    print(f"{'陷阱类型':<14} {'裁判给的忠实度':<14} {'上限':<6} 结果")
    print("-" * 50)

    failures = 0
    for case in CANARY_CASES:
        score = judge(case["question"], case["context"], case["bad_answer"])
        faithfulness = score["faithfulness"]
        limit = case["max_acceptable_score"]
        ok = faithfulness <= limit
        if not ok:
            failures += 1
        print(f"{case['trap']:<14} {faithfulness:<14} {limit:<6} {'✅' if ok else '❌ 裁判被骗了'}")

    print("-" * 50)
    print(f"通过 {len(CANARY_CASES) - failures}/{len(CANARY_CASES)}")
⭐ 这个测试的价值：
它的作用	说明
发现裁判的盲区	比如"流畅但错"的答案，它是不是总给高分
改 prompt 的依据	发现它被流畅性骗 → 在 prompt 里加"流畅不等于正确"
持续监控	每次改 prompt，重跑一遍，看有没有退化


⚠️ 校准集不需要很多 —— 10~20 条就够。

关键是每条都要"坏得明确"。
② 规则交叉验证
有些错误，规则能抓，裁判不该漏。

做法：两边结论矛盾时，人工看。
def cross_check(answer: str, context: str, judge_score: dict) -> str:
    """规则和裁判交叉验证。"""

    # 规则 1：答案里有没有引用
    if not re.search(r"\[\d+\]", answer):
        if judge_score["faithfulness"] >= 4:
            return "⚠️ 答案没有引用，裁判却给了高忠实度 —— 可疑"

    # 规则 2：答案里的数字，资料里有吗
    answer_nums = set(re.findall(r"\d+", answer))
    context_nums = set(re.findall(r"\d+", context))
    fake_nums = answer_nums - context_nums
    if fake_nums and judge_score["faithfulness"] >= 4:
        return f"⚠️ 答案里有资料中没有的数字 {fake_nums}，裁判却给高分 —— 可疑"

    return "✅ 无明显矛盾"
⭐ 规则不需要覆盖所有情况 —— 它只要能抓"明显矛盾"就够了。

抓到一个矛盾案例，你就知道裁判在某类问题上不可靠。
③ 多裁判投票
一个裁判可能被骗，三个裁判同时被骗的概率低得多。
def judge_committee(question, context, answer) -> dict:
    votes = []
    for model in ["deepseek-chat", "qwen-plus", "glm-4"]:
        s = judge_with(model, question, context, answer)
        votes.append(s["faithfulness"])

    return {
        "scores": votes,
        "avg": sum(votes) / len(votes),
        "disagree": max(votes) - min(votes) >= 2,   # 分歧大
    }
⭐ 关键规则：
如果三个裁判的分差 ≥ 2 分，说明存在分歧 —— 这条送人工。

分歧本身就是"我不确定"的信号。
④ 人工抽检（唯一能"证明"的）
这是最朴素，也最不可替代的一层。
做法	说明
每次评测抽 10%	比如 100 条抽 10 条
看裁判的分数和理由	是否和你的判断一致
记录不一致的案例	这是校准集的来源


⭐ 抽检不是为了"发现每一处错误"，而是为了"知道裁判大概多可靠"。

抽 10 条，有 1 条明显判错 → 裁判准确率约 90% → 可以用，但要谨慎。

抽 10 条，有 3 条判错 → 30% 错误率 → 这个裁判不能用。
⑤ 线上监控（有用户之后）
用户的行为是最真实的信号：
信号	说明
用户点了"没用"	答案可能有问题
用户追问"你确定吗"	说明他不信
用户手动改了答案	原答案有错
同一个问题反复问	上次答得不好


⭐ 把这些"负反馈"收集起来，和裁判的分数对比：
裁判给 5 分的答案里，有多少被用户点了"没用"？
如果比例高 → 裁判在"高分区"不可靠。
⭐ 最有效的一个组合
如果你只能做一件事：
建 10 条校准集，跑一遍，看裁判会不会被骗。

为什么？
优点	说明
成本极低	10 条 × 1 次调用
立刻能发现问题	不用等 100 条评测
可复用	每次改 prompt 都跑一遍


这就是"用最少的成本，验证最关键的假设"。

一句话总结
"裁判会不会被骗" 这件事，永远不能靠"我觉得它挺严的"。
你必须用"故意做坏的答案"去试它。

⭐ 而且要注意：骗裁判的，和骗人的是同一套东西 —— 流畅、专业、详细。
所以"看起来很好的答案"，恰恰是最需要警惕的。

⭐ 所以真正的问题不是"judge 够不够强"，而是"judge 靠不靠谱"
这四个字是可以量化的。
方法一：算"一致率"（最实用）
人工标注 100 条（人判断 A 好还是 B 好）
让 judge 也判这 100 条
算两者一致的百分比
一致率	结论
> 85%	✅ judge 可用
70~85%	⚠️ 能用，但结论要谨慎
< 70%	❌ judge 不可靠，换一个


⭐ 这是唯一能"证明"judge 可信的办法 —— 而不是"我觉得它挺准的"。

方法二：用多个 judge 投票
评顶尖模型时，单个 judge 确实不够。

常见做法：
Judge 1（比如 Gemini）→ 判 A 好
Judge 2（比如 Qwen）  → 判 A 好
Judge 3（比如 GLM）   → 判 B 好

→ 2:1，判 A 好
⚠️ 三个 judge 都说"分不出" → 那就真的是分不出。
方法三：给参考答案（Reference-based）
如果有 gold answer，judge 的任务就从"谁更好"变成"谁更接近标准答案"。

这比"纯主观比较"容易得多 —— 因为有了客观锚点。
方法四：承认天花板
⭐ 这是最重要的一条：
如果两个模型都好到"人眼也难分"，那"谁更好"本身可能就是伪命题。

这时候你应该看的不是"质量"，而是：
维度	例子
成本	每百万 token 差多少
延迟	首字延迟差多少
稳定性	哪个更少报错
特定任务	在你的场景里，哪个更少踩坑

| 你的担忧 | 实际情况 |
|---|---|
| "judge 比选手弱，评判没意义" | **不一定** —— 识别能力 ≠ 生成能力 |
| "那怎么知道 judge 靠不靠谱" | **算一致率**（人工 100 条 vs judge），> 85% 才算可信 |
| "评顶尖模型怎么办" | **多 judge 投票 + 人工专家 panel** |
| "如果判断不出呢" | **"分不出"本身就是结论** —— 去看成本/延迟，别纠结质量 |

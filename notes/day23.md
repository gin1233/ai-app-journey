## 软删除

**硬删除和软删除的 SQL 分别长什么样**：
DELETE FROM notes WHERE id = 5;
UPDATE notes SET deleted_at = now() WHERE id = 5;
**用"纸篓 vs 碎纸机"解释**：
软删除 = 扔进纸篓（还能捡回来）
硬删除 = 直接碎掉
**软删除的三个好处**：
出了事能查	"这条笔记怎么没了？" → 翻日志
能追责	是 AI 删的，还是人删的
能复盘	哪些操作最常被触发

## ⚠️ 软删除最大的坑

**为什么所有查询都要加 `deleted_at IS NULL`**：
① 搜索会搜到已删的笔记
你刚才就撞到了：
搜索「测试会议」→ 搜到: 1 条
  id=8  deleted_at=2026-10-31 05:01:43
用户明明删了，搜索却还给他。

用户反应： "我删了啊，怎么还在？" → 以为删除功能坏了。
② 按 id 还能读出来
GET /notes/8 → 200，返回内容
用户删了，但只要知道 id 还能读。

⚠️ 这不只是"体验差"，是"删除没生效"—— 如果这是敏感数据，就是真事故。
③ 列表里还会出现
GET /notes 返回列表 —— 已删的笔记混在里面。

用户看到： 删了 3 条，列表还是 10 条。
④ 统计数字会错
比如"你一共有 10 条笔记"，但其中 3 条已删 —— 实际只有 7 条。

这类数字错误，用户很难察觉，但一旦发现就很尴尬。
**如果只改了 search 忘了 get，会出现什么"半死状态"**：
操作	结果
搜索	搜不到（过滤了）
按 id 读	还是能读到
整体状态	半死状态

**为什么有些团队宁愿用硬删除 + 备份**：
软删除的"记得过滤"太容易漏。取舍：能恢复 vs 容易出错。

## ⚠️ Fail closed vs Fail open
Fail closed（保守）
日志失败 → 业务也失败

金融、医疗、合规场景

Fail open（可用优先）
日志失败 → 业务照常

普通产品，可用性优先

**我用的哪种，为什么**：
 fail open（审计失败不影响业务）
## 批量操作怎么确认

数量	处理方式
1 条	普通确认框
2–9 条	列出清单，一次确认
≥10 条	列出清单 + 要求输入数量确认
**"≥10 条要求输入数量"这个设计，和哪个真实产品类似**：
GitHub 删仓库要你手打仓库名，就是"要求你付出额外动作"来防止手滑。

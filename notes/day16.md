## 为什么不能用 JSON 传文件

**JSON 里能放什么**：
JSON 里只能放文本：字符串、数字、布尔、数组、对象。
**文件是什么**：
文件是二进制数据 —— 一堆字节。塞不进 JSON。
**`multipart/form-data` 是干什么的**（用"寄快递"类比）：
纸条	表单里的文字字段	filename = "报告.pdf"、user_id = "42"
手机	文件的原始字节	PDF 的 %PDF-1.7...、图片的 \xFF\xD8\xFF...

## `UploadFile` 和 `bytes` 的区别

| | `bytes` | `UploadFile` |
|---|---|---|

| 大文件 | 内存爆炸 | 可以 |

**⭐ 为什么大文件用 `bytes` 会出事**：
会挤爆内存 服务器挂 所有人都用不了

操作系统会直接杀掉占用内存最多的进程。
也就是你的 FastAPI 服务被系统杀死。
所有用户的请求同时失败 —— 不只是那三个人。

崩溃 → 重启 → 用户又传大文件 → 再崩溃 → 再重启 → ...

## 三个必须防的坑

| # | 坑 | 后果 | 防法 |

| ① | 文件太大 | 内存爆 / 磁盘爆 | 前端限制+后端流式读取|

..\..\.. 会不停往前一个文件夹走 攻击者会撤到c盘植入.exe文件攻击

**防法是什么**：

只取最后一个safe_name = Path(file.filename).name 忽略..

## 为什么用两张表，不用一个 JSON 字段

| 方案 | 结构 | 问题 |
|---|---|---|
| A | 一张表+json | 不灵活强制你解析json里所有信息then找到最相关 可行慢但是json文件很大就等到死 |
| B | 两张表 | 灵活可以直接找到最相关的文件不必把所有chunk读一遍，且可以修改其中任意chunk |

**⭐ 为什么选 B（三个理由）**：
1. 灵活可修改可删除
2. 速度快
3. 快速索引

## ⭐ `flush()` 和 `commit()` 的区别
flush = 把改动推给数据库，拿到结果（比如 id），但还没"按确认键"。
commit = 按确认键，永久生效。
| | `flush()` | `commit()` |
|---|---|---|
| SQL 发了吗 | 发了 | 发了 |
| 有 id 了吗 | 有 | 有 |
| 事务提交了吗 |没 | 提了|
| 能撤回吗 |能 | 不能 |

**为什么这里必须先 `flush()`**：
因为 DocumentChunk 需要 document_id。而 document.id 是数据库插入时才生成的。

**用"填快递单"类比**：
flush 填表拿号
commit 交给快递员
**如果不 flush 直接 commit，会怎样**：
不 flush 的话，document.id 还是 None → 插 chunk 时会报"外键为空"。
**这样写还有个额外的好处是什么**（提示：中途出错）：
中途出错可以回滚

def clean_text(text: str) -> str:
    """清掉无法编码成 UTF-8 的字符。

    为什么需要？
        PDF 的字体映射偶尔会吐出「孤立代理字符」
        （U+D800~U+DFFF，比如 \\ud83d）。
        这种字符在 UTF-8 里是非法的，存进数据库会报
        UnicodeEncodeError。
    """
    return text.encode("utf-8", errors="ignore").decode("utf-8")

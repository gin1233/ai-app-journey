## 流式解决的问题

**现在的非流式体验**（`/ai/chat`）：等几秒，一股脑输出。

**用户的感受**：
我是觉得都 ok，可能少了点参与感，不知道 AI 是否在工作。我觉得好的前端可以解决这个问题，当然流式更直观地告诉你 AI 在工作。

**流式之后的体验**：打字机效果，就像我说的，还行。

**⚠️ 但"前端加 loading 能解决吗"这个问题，我漏了一半：**

| | 前端加 loading 动画 | 流式 |
|---|---|---|
| 解决什么 | **知道系统没死** | **内容已经开始产出了** |
| 用户等多久 | **总时长不变**（还是等 10 秒） | **首字 1 秒，然后边看边等** |
| 心理感受 | "它在转圈" | **"它在说话"** |

**⭐ 关键指标：TTFT（Time To First Token，首字延迟）**

> 用户感知的等待时间，**不是"总耗时"，而是"看到第一个有意义内容之前的时间"**。
>
> 一段 10 秒生成完的回答：
> - 非流式 → 感知等待 **10 秒**
> - 流式 → 感知等待 **1 秒**
>
> **总耗时一样，体感差 10 倍。**

**流式还有一个隐藏好处**：用户可以**提前判断答歪了，早点打断重问** —— 省时间也省钱。**这是 loading 动画永远做不到的。**

**用餐厅类比**：

| | 非流式 | 流式 |
|---|---|---|
| 上菜方式 | 不透明厨房，所有菜做好了再一起端上来 | 透明厨房，厨师当着你的面做，做好一道端一道，**像 omakase 一样** |
| 用户体验 | 小菜馆 | **明厨亮灶 omakase** |

## ⭐ `yield` 的第三次出场

| 课次 | 在哪 | 用途 |
|---|---|---|
| Day 08 | `database.py` → `get_db` | **依赖注入**：把 db 交出去，用完自动 close |
| Day 11 | `llm.py` → `stream_chat` | **流式输出**：产出一段，立刻交出去 |

**`yield` 和 `return` 的本质区别**：

| | `return` | `yield` |
|---|---|---|
| 交出去之后 | **函数结束**，栈销毁 | **函数暂停**，原地不动 |
| 还能继续吗 | ❌ | ✅ **等你来要下一个，从原地继续** |
| 一次能给多少 | 一个值 | **可以给很多次** |

> **一句话**：`return` 是"干完活就跑路"，`yield` 是"**说完一句就暂停，等你来要下一句**"。

**Day 08 那个 A→B→C 的最小例子，现在怎么解释流式**：

```
A：函数开始（连上大模型）
B：yield 交出一个字 → 函数暂停
   ← 此刻接口层把 "data: 你\n\n" 推给浏览器
C：函数继续，取下一个字
（循环 B、C，直到模型说完）
```

**每 yield 一次，就等于往浏览器推了一次数据。**

## SSE 是什么

**全称**：Server-Sent Events（服务器推送事件）

**格式规则**（两条）：

1. **每行以 `data: ` 开头**
2. **空行（`\n\n`）表示一条消息结束**

```
data: 你

data: 好

data: [DONE]

```

**`[DONE]` 是谁规定的**：**社区约定，不是协议规定的**。用来告诉客户端"流结束了"。

**SSE 和 WebSocket 的区别**：

| | SSE | WebSocket |
|---|---|---|
| 方向 | 单向（服务器 → 浏览器） | 双向 |
| 底层 | **就是普通 HTTP** | **独立协议，需要升级连接** |
| 断线重连 | **浏览器自动重连** | **要自己写** |
| 复杂度 | 低 | 高 |

**为什么大模型对话用 SSE 就够了**：交互模式是"**你发一次，我流式回一次**"，不需要双向实时通信。

**面试题：ChatGPT 那种打字机效果怎么实现**：
**服务端用 SSE 流式返回，前端边收边渲染。**

## `stream_chat` 里的三个细节

### ① `stream=True`

**加了这一行之后，返回值变成了什么**：
从"一个完整的响应对象"变成 **一个迭代器** —— 可以一段一段地取。

### ② `delta` 和 `message` 的区别

| | 非流式 | 流式 |
|---|---|---|
| 取值路径 | `chunk.choices[0].message.content` | `chunk.choices[0].delta.content` |

**`delta` 是什么意思**：**增量** —— 表示"这次比上次**多了**哪些字"，不是完整内容。

### ③ 为什么必须写 `if piece:`

**哪些 chunk 的 `delta.content` 会是 None**：**通常最后一个 chunk**（只是个结束标记，不带内容）。

**不判断会怎样**：
`yield None` → `json.dumps(None)` 得到 `"null"` → 前端 `JSON.parse("null")` 得到 `null` → `textContent += null` **会拼出字符串 "null"**。

**用户会在回答末尾看到莫名其妙的一个 "null"。**

## `routers/ai.py` 里的三个细节

### ① `StreamingResponse` 和普通返回的区别

| | 普通返回 | StreamingResponse |
|---|---|---|
| 你返回什么 | 一个**值**（dict / 对象） | 一个**生成器** |
| FastAPI 怎么发 | 全部序列化好，**一次发完** | **边产边发**，生成器吐一个就发一个 |

### ② 为什么 `to_sse` 要单独拆一层

**如果把 SSE 格式直接写在 `services/llm.py` 里，会有什么问题**：
**服务层就依赖了 HTTP 协议**。以后想换成 WebSocket，必须动服务层。

**这体现了分层的什么价值**：**换一层不用动另一层。**

```
services/llm.py   →  产出纯文本片段（"你"、"好"、"世界"）
routers/ai.py     →  包装成 SSE（"data: 你\n\n"）
```

### ③ 为什么必须 `json.dumps`

**模型输出的文字里可能有什么字符会破坏 SSE 协议**：**换行符（`\n`）**。

**不转义会怎样**：
SSE 里「换行 + 空行」是消息分隔符。模型输出里夹一个换行，**一条消息会被切成两条**，客户端解析出错。

**`ensure_ascii=False` 是干什么的**：

| 写法 | 输出 |
|---|---|
| `json.dumps("你好")` | `"\u4f60\u597d"` ← 能解析，但看不懂 |
| `json.dumps("你好", ensure_ascii=False)` | `"你好"` ✅ |

## ⚠️ 为什么不能用 `/docs` 验证流式

**Swagger UI 会怎样**：**会把整个响应缓冲完再显示** —— 你看到的是"一次性出现"，感受不到流式。

**PowerShell 的 `curl` 是什么**：**`Invoke-WebRequest` 的别名**（不是真正的 curl），**它也会缓冲**。

**正确的验证方式**：用 Python 的 `httpx`，`iter_lines()` 边收边打印。

## 彩蛋：前端 `buffer` 的作用

```javascript
buffer += decoder.decode(value, { stream: true });
const lines = buffer.split("\n");
buffer = lines.pop();          // ← 为什么需要这一行
```

**为什么"收到的数据块"和"行"的边界会对不齐**：
**网络数据包的大小和"行"的边界毫无关系。**
比如服务器发了 `data: 你好\n\ndata: 世界\n\n`，**第一次 `read()` 可能只收到 `data: 你`** —— 半截。

**如果不用 buffer 会怎样**：
最后那半截被当成完整行 → `line.startsWith("data: ")` 判断为 True → `JSON.parse("你")` **直接抛异常**。

**核心思想：流式数据是"碎"的，任何时候都要处理"边界对不齐"。**

## 还没搞懂的地方

**Q：如果用户中途关闭网页，服务器这边的生成器会怎样？**

→ 生成器会被**丢弃**（内存回收）。但**大模型的请求可能还在跑** —— **钱已经花了**。
→ 生产环境要监听 `request.is_disconnected()` 主动中断，及时止损。

**Q：流式输出怎么统计 token 用量？**

→ 非流式看 `response.usage`。流式要用 `stream_options={"include_usage": True}`，
**最后一个 chunk 里会带上 usage**（不是每个 chunk 都有）。

**Q：为什么 SSE 用 POST 而不是 GET？前端为什么用 fetch 而不是 EventSource？**

→ **SSE 协议本身只定义了 GET，浏览器的 `EventSource` API 也只支持 GET。**
→ 但对话需要发一大段 prompt，**塞进 URL 不合适**（长度限制、还会被记进访问日志）。
→ 所以只能用 **`fetch` + POST + 手动读 `ReadableStream`**。
→ **代价**：失去了 `EventSource` 自带的**自动重连**，要自己实现。

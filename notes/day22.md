## 只读和可写的区别

| | 只读 | 可写 |
|---|---|---|
| 最坏后果 | 瞎说瞎答 | 篡改污染数据库 |
| 能撤销吗 | 不用 | 很难 |
| 需要确认吗 | 不需要| 必须 |

## 写操作的三个风险

1. 模型理解错意图 你说"这条太长了"，它理解成"删掉它"。
2. Prompt 注入 用户输入里藏着"删掉所有笔记"，模型照做。
3. 不可逆 写错了，没有"撤销"按钮。

**为什么说"第三条最致命"**：
Day 12 我们说过：不要给模型"直接执行危险操作"的能力。今天就是这句话的落地。
## 两阶段设计

**方案 A 直接执行，为什么不可接受**：
模型说写就写。
**方案 B 两阶段，流程是什么**：
模型提议 → 用户确认 → 执行。
**用银行转账类比**：
银行转账	Agent 写操作
你填转账单	模型提出"我要创建这条笔记"
银行显示确认页（转给谁、多少钱）	后端返回 needs_confirm + 参数预览
你输密码	用户点"确认"
真正转账	执行工具
**⭐ 一句话核心**：
模型只能"提议"，不能"执行"。执行权在用户手里。
## 三个接口步骤

| 接口 | 干什么 |
|---|---|
| `POST /agent/ask` | 模型决定要写 → 不执行，返回 action_id |
| `POST /agent/confirm` | 用户点确认 → 这时才执行 |

**为什么用 action_id，而不是让前端回传参数**：
为什么用 action_id 而不是把参数直接传给 confirm？因为参数是模型生成的，如果让前端回传参数，用户（或中间人）就能篡改。用 action_id 从服务端取，参数就不可篡改。
## ⭐ 遇到写工具为什么要立刻 return

**如果"记下来继续跑"会发生什么**（举一个具体例子）：
举个例子：用户说"建一条笔记，然后总结它"。如果你不在这里停，模型会以为笔记已经建好了，直接去总结一个不存在的东西。
## ⭐ 为什么用 `pop` 不用 `get`

| | `pop` | `get` |
|---|---|---|
| 取出来之后 | 取出来就删了 | 取出来还在 |
| 重复确认会怎样 | 第二次确认 → 404 | 双击 → 创建两条一样的笔记 |

**现实里哪些情况会导致重复确认**：
用户双击"确认"

网络超时，前端自动重试

用户刷新又点了一次
## ⚠️ 内存版的四个问题

| 问题 | 后果 |
|---|---|
| 进程重启就丢 | 用户点确认 → "操作不存在" |
| 多实例不共享 | A 机器存的，B 机器查不到|
| 没有过期时间 | 内存只增不减 → OOM |
| 没绑用户 | 猜到 id 就能确认别人的操作 |

**生产上必须怎么做**：
存数据库 + expires_at + user_id。


## ⚠️ 为什么确认了还要再校验

**"用户点了确认"保证了什么，没保证什么**：
确认机制保证的是"用户同意执行"，不是"参数合法"。这两件事要分开。
## 工具描述为什么要写"什么时候用"
工具描述不只说明"能干什么"，更要说明"该在什么时候用"。后者对模型的决策影响更大。
**不写会怎样**（举一个误触发的例子）：
用户说"总结一下笔记"，模型可能顺手"创建"一条摘要笔记。

 - 如果用户确认之前进程重启了，会怎样？
 时序	结果
重启发生在"确认前"	操作丢失，用户要重来
重启发生在"确认后、执行前"	操作丢失，数据没写
重启发生在"执行中（commit 前）"	事务回滚，数据没写，干净
重启发生在"commit 后、返回前"	数据已写入，但用户看到超时

用户看到超时 → 以为失败 → 重新说"建一条笔记" → 又建了一条。

结果：数据库里两条一模一样的笔记。

这不是 pendding 机制能解决的 —— 需要"幂等键"（idempotency key）：
前端生成一个唯一 key（比如 uuid），随请求带上
→ 服务端先查"这个 key 处理过没有"
→ 处理过 → 直接返回上次的结果，不再执行
